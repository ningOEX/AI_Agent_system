# 从 0 到 1 打造「博客 + 后台 CMS + 智能客服」三端一体系统：技术总结

> 一个独立完成的全栈项目：Vue 3 前台 + Vben Admin 后台 + Express/MongoDB 后端 + Docker 部署。
> 本文记录其中值得展开的设计决策与踩坑，而非功能罗列。

## 一、项目全貌

系统由三部分组成，共享同一个后端：

- **blog-web（前台）**：Vue 3 + Tailwind + GSAP，面向访客，无需登录即可阅读、评论、使用智能客服
- **client（后台）**：Vben Admin 5 + Ant Design Vue，面向作者/管理员，管理内容、客服会话、监控数据
- **server（后端）**：Express 4 + Mongoose 8，JWT 认证，SSE 流式输出，Docker Compose 编排部署

三个亮点模块的设计思路值得单独讲：**智能客服三级兜底**、**审计留痕与一键回滚**、**AI 流式集成**。

## 二、智能客服：三级兜底与「等待人工」状态机

### 2.1 三级兜底链路

客服回答不是直接丢给大模型，而是分层降级，兼顾成本与效果：

```
用户提问
  → L1：FAQ 精确/模糊匹配（内存缓存 5 分钟，零成本，命中即回）
  → L2：知识上下文检索（把已发布博客作为上下文，缓存 10 分钟）
  → L3：DashScope 大模型生成（SSE 流式输出，对话级缓存 1 小时）
  → 兜底：引导用户「转人工」
```

两个关键的工程决策：

1. **sessionId 必须由后端签发**。前端不允许自己生成 UUID——否则任何人都能伪造会话身份绕过限流。首次请求无 sessionId 时，后端生成并通过响应体 + SSE done 事件双通道下发，前端持久化到 localStorage。
2. **限流按 IP + sessionId 双维度**。单 IP 60 秒窗口最多 10 次，超限返回 429 并带 `Retry-After` 头。只限 IP 会误伤 NAT 出口下的多个真实用户；只限 sessionId 则换个会话就能绕过。

### 2.2 「等待人工」是一个永久锁定的状态

转人工最容易踩的坑是：用户转人工后再发消息，机器人又抢着回答了。我的设计是：

- 点击转人工后，会话进入 `awaitingAgent` 模式，后续用户消息**只入库、不触发任何自动回复**
- 该状态是**永久锁定**——管理员在后台回复也不会解锁（否则用户每句话都可能被人机混合抢答）
- 唯一的解锁方式是用户主动关闭并重新打开聊天弹窗，调 `POST /chat/sessions/:id/reset`

语义上也要克制：前台聊天气泡统一显示「客服回复」，后台会话详情才显示「管理员回复」；用户自己的消息不展示来源标签，避免出现「来源：ai」这种错误语义。

### 2.3 会话存储的体积控制

聊天消息内嵌在会话文档里会持续膨胀，最终撞上 MongoDB 16MB 单文档上限。方案：

- ChatSession 单文档最多保留 50 条消息，溢出自动归档到独立的 ChatMessageArchive 集合
- 会话集合加 90 天 TTL 索引，归档集合 180 天，无活跃会话自动清理
- 后台会话列表用聚合管道查询，只拉每条会话的最后一条消息 + 总数，绝不拉完整 messages 数组

## 三、审计留痕：不只是日志，而是可回滚的快照

### 3.1 设计目标

留痕模块记录所有写操作（新增/修改/删除），并且**能一键恢复到变更前的状态**。这意味着不能只记「谁改了什么」，必须存变更前后的完整数据。

实现上是 Express 中间件 + Mongoose 钩子的组合：

- 写操作触发时，先查出当前文档作为 `before` 快照
- 操作成功后，新文档作为 `after` 快照
- 删除操作额外保留完整文档，否则无法还原

### 3.2 恢复逻辑按动作类型区分

| 动作 | 恢复语义 |
|---|---|
| delete | 把被删数据重新入库（**保留原 _id**，避免引用断裂） |
| update | 回滚到 before 快照 |
| create | 撤销新增，删掉当时创建的记录 |

并非所有模块都可恢复：上传文件没有业务文档、客服会话主键非 ObjectId，这两个模块显式列入黑名单。

### 3.3 列表聚合与时间线

同一条业务内容可能被反复修改，列表如果每次都展示一条就没法看。规则是：

- 列表按 `module + targetId` 分组聚合，只展示最新一条，附带「共 N 次」标签
- 详情抽屉里展示该对象的完整改动时间线，可点击切换到任意一次查看当时的快照

### 3.4 权限：严格按账号隔离

所有用户（**包括 admin**）只能查看、操作、恢复自己的留痕记录，没有全局查看特权。这是一个刻意的选择：留痕涉及数据快照，admin 能看所有人的快照等于拥有了全站数据的读权限，攻击面太大。

## 四、AI 流式集成：SSE 落地的四个坑

AI 写作助手和智能客服都用 SSE（Server-Sent Events）流式输出。看似简单，实际踩了四个坑：

1. **Nginx 缓冲截断**。默认 `proxy_buffering on` 会把流式响应攒成一整块再吐给浏览器，用户看到的是「转圈 30 秒后一次性弹出全文」。必须 `proxy_buffering off` + 调大 `proxy_read_timeout`（300s）。
2. **文生图超时**。图片生成耗时长，HTTP 客户端默认超时（通常 30-60s）必然失败，显式设置 ≥ 120 秒。
3. **密钥缺失的优雅降级**。`DASHSCOPE_API_KEY` 未配置时，AI 接口返回 503 而不是 500，前端据此提示「AI 功能未启用」，其余业务完全不受影响。
4. **内容声明联动**。用 AI 生成正文时，收到第一段流式内容就自动把文章 `contentType` 切换为「AI 生成」；但生成失败或手动停止时**不修改**已设置的声明——状态联动只在一个方向上做，避免误标。

## 五、认证体系：Token 表的一对多设计

不用「一个用户一个 token」的简单模型，而是独立的 Token 表：

- 一个用户可同时存在多条 Token 记录 → 天然支持**多设备并行登录**
- MongoDB **TTL 索引**自动清理过期记录，不需要定时任务
- 登出只删当前设备那条记录，不影响其他设备
- 修改密码成功后清除该用户**所有** Token，强制全端重新登录——这是安全 baseline

登录和注册接口返回完全相同的 `{ accessToken, user }` 结构，前端注册成功后复用同一套 store 初始化逻辑直接完成自动登录，不用跳转登录页再输一次密码。

## 六、媒体资源：延迟上传与垃圾清理

### 6.1 封面图延迟上传

用户选了图就立即传 OSS 的做法会产生大量垃圾文件（选了又换、换了不保存）。改为：

- 选择图片后只在前端生成 blob 预览，**不上传**
- 点击「保存文章」那一刻才真正上传 OSS
- 文章保存的是 OSS 公开 URL，草稿再次编辑时能正确回显

### 6.2 旧文件异步清理

替换或移除封面后，前端收集所有被替换的旧 OSS 地址，在文章**保存成功后**批量异步删除。注意顺序：必须先保存成功再删旧图，否则保存失败时文章会引用一个已被删除的 URL。

### 6.3 为什么后端中转而不是前端直传

阿里云 OSS SDK 6.x 的 `signatureUrl` 对 PUT 请求存在签名计算错误，前端直传会 403。改为后端 `client.put()` 中转上传，顺带解决了跨域配置和密钥暴露问题。

## 七、内容安全：敏感词检测的对抗性设计

简单的关键词 `includes` 匹配会被轻松绕过。实际做了三层：

1. **归一化**：去除零宽字符、全角转半角、去分隔符（如「敏 感 词」「敏.感.词」）
2. **白名单豁免**：合法语境中的敏感词片段不误拦（如技术文章里的正常词汇）
3. **字段级错误定位**：命中返回 422 + 具体字段路径，前端全局错误拦截器直接提示，零改动接入

整个功能由 `CONTENT_FILTER_ENABLED` 环境变量开关控制，关闭时自动跳过，不影响原有流程。

## 八、工程化踩坑实录

这部分大概是面试中最有谈资的——都是文档里查不到的问题：

| 问题 | 根因 | 解法 |
|---|---|---|
| 生产环境登录后白屏报错 | pnpm workspace 把 vue-router 打包成两份实例，`useRouter()` 返回 undefined | `vite.config.ts` 加 `resolve.dedupe: ['vue-router']` |
| Express 通配路由 404 | Express 5 的 `'/route/*name'` 语法在 Express 4 不支持 | 用 `'/route/*'` + `req.params[0]` |
| Tailwind 样式全失效 | Tailwind v4 在 Vite 8 下 content 扫描失效 | 退回 v3 + PostCSS 稳定方案 |
| 地址栏 token 残留 | 清理逻辑在 JS bundle 里，加载慢时来不及执行 | 前移到 `index.html` 内联脚本，HTML 解析阶段即清理 |
| 服务器上 rm 命令卡死 | 系统 alias `rm -i` 交互模式等待输入 | 脚本里统一用 `/bin/rm` 绕过 |
| DatePicker 值不同步 | antd v4 对 reactive 对象内 dayjs 属性响应式异常 | 独立 ref 存 ISO 字符串，computed 适配 dayjs |

部署侧的经验：2 核 2G 服务器跑不动 Vben 构建（OOM），改为**本地构建 + dist 提交仓库 + 服务器直接挂载**，web 容器零构建；后端重建封装成 `update-api.sh` 一键脚本（拉代码 → rsync 同步保留 .env → 重建镜像 → 健康检查），全程不碰 MongoDB 数据卷。

## 九、可观测性：埋点先于监控

没有上 Prometheus（2G 内存限制），但做了轻量替代：

- **接口监控**：中间件全量埋点 HTTP 请求，后台可查看调用分布、慢接口、错误率，接口文档与目录共用同一份数据源（`apiCatalog.js`），新增路由只需补一条配置
- **AI 用量统计**：每次大模型调用记录 token 消耗并折算费用，防止额度被刷爆还不知道
- **操作留痕**：见第三章

这套组合的哲学是：**小项目不需要重型监控栈，但埋点数据必须先存下来**——有了数据，以后接任何可视化都来得及。

## 十、总结

这个项目对我最大的价值不是「又做了一个博客」，而是把几个真实的工程问题想清楚了：

- **状态机设计**（等待人工锁定）比堆功能更重要
- **可逆操作**（留痕回滚）要求从第一天就存快照，事后补不了
- **成本意识**贯穿始终：FAQ 缓存、对话缓存、限流、延迟上传、TTL 清理，每一处都在防「小钱变大钱」
- **部署友好性**是设计出来的：环境变量开关降级、本地构建零服务器依赖、一键更新脚本

技术栈并不新，但每个决策都有明确的 trade-off 理由——这大概就是这个项目最值得展示的部分。
